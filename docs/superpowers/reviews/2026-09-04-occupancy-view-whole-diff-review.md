## Findings

### F1 — apply_zoom_lock() unlocks the decorative y2 "when" strip when chart-zoom is enabled  [Minor]
File: btc_web/callbacks/charts/__init__.py:884 (`apply_zoom_lock(fig, "chart_zoom" in toggles)`); btc_web/figures/common.py:494-509
Claim: `apply_zoom_lock(fig, zoom_on, axes=True)` calls `fig.update_yaxes(fixedrange=not zoom_on)` with no `selector`, which in Plotly applies to every y-axis on the figure, including `yaxis2`.
Evidence: `figures/occupancy.py:186-193` sets `layout["yaxis2"] = dict(..., fixedrange=True, ...)` deliberately (the "when" strip is meant to stay fixed — 2 tick rows in a 7%-tall paper region), but `common.py:507-508` (`fig.update_xaxes(fixedrange=not zoom_on); fig.update_yaxes(fixedrange=not zoom_on)`) is generic and overwrites that per-axis choice whenever the user has "Enable chart zoom" checked.
Failure scenario: user checks "Enable chart zoom" in `bub-toggles`, then opens the Occupancy pill → `yaxis2.fixedrange` becomes `False`, so the narrow "when" strip becomes independently draggable/zoomable (its 2-row layout can be panned out of the fixed `[0.4, 2.6]` view). Not a wrong-result or data bug — cosmetic interactivity papercut confined to a 7%-tall strip, and the same generic call is already used unconditionally elsewhere in the codebase (e.g. dual-y charts), so this is an inherited limitation rather than a new class of defect.
Suggested fix: pass `axes=False` (or a yaxis2-aware selector) from `update_bub_occ`, or re-assert `fixedrange=True` on `yaxis2` after `apply_zoom_lock` runs.
